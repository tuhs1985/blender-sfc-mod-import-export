# SFC20Converter reference review

Reviewed 2026-11-26 from the user-provided `SFC20Converter.rar`. The archive is retained locally outside Git; its contents were extracted only into ignored `output/reference-sfc20`. No included executable or script was run during this review. Findings below are from static source inspection and the included PDFs.

The package credits Berto Armando Perez (Centurus) for direction and testing and Claude for coding. It includes a single-file Blender add-on, a browser-based HTML converter/viewer and three PDF guides. Its guides describe the package as free to use and request retaining credits when sharing; no broader source-code license was identified in the material reviewed. Treat its source as reference rather than copying code or redistributing it without checking its terms.

## Blender add-on

- Its guide says a known model import was tested in Blender 4.1, but Blender export was not yet confirmed; remaining add-on behavior was simulated. This is the author's reported status, not a current independent test.
- It supports LODs, break groups, named Empty points, diffuse and illumination images, modifiers and LOD distances/tolerance. Selection and model type are chosen manually; it defaults to all scene objects and a single merged model. Imported point objects are placed in a separate collection. It warns when no points are exported.
- It reads stored corner normals into Blender and exports evaluated corner normals directly, including inverse-transpose transformation. Our add-on instead uses an optional split-vertex approach and recalculates normals; the user reports that approach worked on a real model. The alternative is worth investigating, but OP rendering of arbitrary corner normals has not been established here.
- Its import option to weld coincident vertices defaults to on. This may join intentional detached boundaries used in the user's SFC smoothing workflow; its importer also attempts to mark sharp edges and set custom normals. Effects need real tests, not assumptions.
- It reconstructs files from parsed records, lowercases written string references, uses Latin-1 with replacement for unencodable characters, and imposes a 65,535-vertex maximum. Our unchanged-source path preserves opaque top-level records, keeps references where possible and supports 65,536 vertices indexed 0–65,535. Runtime limits and any specific encoding beyond ASCII remain separately unverified.
- It registers the same Blender operator identifiers as our add-on (`import_scene.sfc_mod` and `export_scene.sfc_mod`), and its filename overlaps our package name. Enabling both simultaneously may cause registration or module conflicts; use separate Blender configurations when comparing them.

## Browser converter

The guide describes local viewing and conversion among MOD, OBJ and 3DS, plus read-only MAX import for Editable Mesh objects and helpers for Max dummy points. The HTML source contains a MAX reader and user-facing buttons consistent with those descriptions. This offers a potentially useful route for the user's old Max models; broad MAX compatibility, material fidelity, smoothing and game behavior have not been independently checked. Static search found no external script sources or common network request APIs, but this is not a security audit. No real model conversion was run.

## Potential follow-up

If the user wants to explore a MAX-to-Blender workflow, use a copy of a representative `.max` model, compare geometry, points, UVs, materials and orientation in Blender and MOD Viewer, and keep game-derived assets local. Separately, a controlled MOD Viewer comparison could evaluate direct corner normals against our vertex-splitting approach; it would not by itself establish OP renderer behavior.

## Rommie axis comparison — 2026-11-26

The user supplied two local exports of the same model and identified `rommie.mod` as produced by our add-on; `rommie2.MOD` came from the other add-on. Each has one LOD, 20,807 vertices and 41,424 triangles, with no named points. Every vertex corresponds at the same index under `(x, y, z) -> (z, y, -x)`, a 90-degree rotation about the file's Y axis. All 41,424 triangles match by vertex set (corner starting order may differ). Their material counts differ (1 versus 2), so this comparison does not establish equivalent materials or shading.

The model's long dimension is along file Z in our `rommie.mod`, and file X in `rommie2.MOD`. Installed original OP FCA and KCA models have long axes along file X, and their hardpoint locations support X as the ship's longitudinal axis. This is evidence that our newly authored Blender export has an orientation mismatch for this model, while the other file is aligned to the stock longitudinal axis. Final forward/backward direction and rendered orientation should be checked in MOD Viewer or OP; the files contain no points to compare.

The conversion formulas explain the difference: our authored export writes Blender `(x, y, z)` as `(x, z, -y)`; the other tool writes `(-y, z, -x)`, mapping Blender forward `-Y` to file `+X`. Our importer and exporter use inverse transforms, so existing imported MOD round trips can preserve their file orientation even if a newly authored Blender model follows a different forward-axis convention. Changing that convention must account for imported scenes, transforms and points, and must not break existing round trips. No exporter code was changed in this investigation.

**Correction after user feedback:** The user reports that a stock FCA imported by our add-on appears oriented like the Blender screenshot. The screenshot alone does not establish an agreed nose direction or distinguish upright orientation from forward orientation, so the preceding hypothesis must not be treated as a confirmed bug or a reason to change conversions yet. For the installed FCA previously supplied at `C:\Program Files (x86)\Taldren Software Inc\Starfleet Command Orion Pirates\Assets\Models\fca\fca.mod`, the imported world-space mesh spans about 15.77 along Blender X and 7.14 along Blender Y; our `rommie.mod` imports with spans about 4.33 along X and 7.12 along Y. These measurements are of mesh dimensions, not proof of nose direction. Confirm the exact FCA and forward direction with the user and compare the actual viewport/game orientation before deciding which convention is correct.

**User comparison:** After correcting the orientation for comparison, the user reports that the two models look almost the same in MOD Viewer and that their smoothing differences are barely visible. This is a viewer comparison for this model, not an in-game test or proof of equivalence for all models or custom normal cases. The user also found the two Blender add-ons should not be enabled simultaneously because they share operator identifiers.

## Original Max plugin axis handling

The supplied R4 importer readme lists the break-model prompt but no user-selected axis option. Static inspection of the original importer's mesh and dummy-point paths shows fixed `Matrix3::RotateY` followed by `Matrix3::RotateX` calls; the binary's double constants at `0x100040f0`, `0x10004300` and `0x100042f8` evaluate to pi, -0.5 and +0.5, respectively. Thus the importer applies rotations of -90 degrees around Y and +90 degrees around X, in that call order. The R4 exporter has the inverse call sequence: X -90 degrees followed by Y +90 degrees. Exact resulting component mapping depends on Max's matrix composition conventions and has not been checked by running the original plugin. The fixed rotations are evidence of an automatic conversion, not a configurable axis selection.

Autodesk's [Matrix3 C++ API documentation](https://help.autodesk.com/cloudhelp/2022/ENU/Max-Developer-Help/cpp_ref/class_matrix3.html) states that vectors are row vectors and the incremental rotations multiply on the right; its [rotation documentation](https://help.autodesk.com/cloudhelp/2020/ENU/Max-Developer-Help/files/developer/3ds_max_sdk_features/modeling/transformation_and_rotation/matrix_representations_of_3d_tra/rotation.html) describes right-handed positive rotation. Applying those rules to the original plugin's calls gives the importer mapping MOD `(x,y,z)` to Max `(-z,-x,y)` and the inverse exporter mapping Max `(x,y,z)` to MOD `(-y,z,-x)`. These match the other add-on's documented conversion formulas. This is a static derivation from plugin calls and SDK semantics, not an original-plugin runtime test. The user reports that Rommie was deliberately built with SFC export in mind; its original Max orientation and any conversion by the separate MAX importer remain relevant when interpreting Blender screenshots.

After the user requested the original convention, the local v0.4.1 development build adopted these inverse mappings for imports and exports, including points and break geometry. The user subsequently asked to remove compatibility with the earlier v0.4.0 axis conversion; all models now use the same convention. Older scenes may need to be reimported or realigned. Blender background tests cover standard and break scenes, transforms and points; original OP FCA and KCA standard exports remained byte-identical. The user-facing orientation and point checkout is pending.
